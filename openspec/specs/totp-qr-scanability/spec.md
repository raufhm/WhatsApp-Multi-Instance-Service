# totp-qr-scanability Specification

## Purpose

Ensure TOTP enrollment QR codes are scannable and import correctly in Google
Authenticator (and other authenticator apps) by producing a single,
spec-compliant, internally consistent `otpauth://` URI shared by backend and
frontend.

## Requirements

### Requirement: The TOTP enrollment QR code scans successfully in Google Authenticator

A tenant operator during TOTP enrollment MUST be able to scan the displayed QR
code with Google Authenticator and import the account successfully.

#### Scenario: Enrollee scans QR with Google Authenticator

- **WHEN** an operator completes a fresh TOTP enrollment and scans the QR code
  with Google Authenticator
- **THEN** the scan MUST succeed and import a TOTP account
- **AND** the imported account MUST show the expected issuer (matching the
  label prefix) rather than an undefined or mismatched name
- **AND** a 6-digit code generated by the imported account MUST verify
  successfully server-side

### Requirement: The otpauth URI is spec-compliant and internally consistent

The service MUST build the `otpauth://` URI with a label whose provider prefix
matches the `issuer` query parameter, with standard `algorithm`, `digits`, and
`period` parameters, and with correct, consistent encoding.

#### Scenario: URI generation

- **WHEN** the backend generates a TOTP enrollment URI for `account` and
  `secret`
- **THEN** the URI MUST match the pattern
  `otpauth://totp/<issuer>:<account>?algorithm=SHA1&digits=6&period=30&issuer=<issuer>&secret=<base32>`
- **AND** the `<issuer>` inside the label and the `issuer` parameter MUST be
  identical

### Requirement: Backend and frontend produce identical URIs

The frontend fallback URI builder MUST emit the same `otpauth://` string as the
backend for the same issuer, account, and secret.

#### Scenario: Frontend fallback parity

- **WHEN** `TotpQrCode` renders a QR without a backend-provided `otpauthUrl`
- **THEN** the fallback URI MUST be byte-identical to the URI the backend would
  generate for the same parameters
- **AND** no hardcoded demo URIs or divergent issuer spellings MUST appear in
  frontend fallback rendering

### Requirement: URI construction and QR behavior are covered by tests

The full URI (not just a prefix) MUST be asserted by tests, and a round-trip
test MUST verify the QR payload decodes back to a valid otpauth URI.

#### Scenario: Full-URI regression test

- **WHEN** a test calls `GenerateOtpauthURL` with fixed inputs
- **THEN** the output MUST equal the exact expected golden string including the
  issuer parameter and encoding

#### Scenario: QR round-trip test

- **WHEN** a test encodes the otpauth URI to a QR data URL and decodes the QR
  payload
- **THEN** the decoded payload MUST match the original otpauth URI
